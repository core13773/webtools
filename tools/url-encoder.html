About the URL Encoder / Decoder

A URL (URI, defined by RFC 3986) may only carry a limited set of ASCII characters. Anything outside that set — a space, a brace, Hangul, an emoji, or any byte with the high bit set — must be percent-encoded before it can appear in a URL. This tool performs that encoding and its reverse, so you can safely embed arbitrary text in a path or query string and recover the original later. Everything runs in your browser; nothing is sent anywhere.

How it works

Percent-encoding writes a byte as a percent sign followed by two hexadecimal digits: %XX. RFC 3986 splits characters into two groups. Unreserved characters — A–Z, a–z, 0–9, and - . _ ~ — never need encoding because they have no special meaning. Reserved characters — the gen-delims : / ? # [ ] @ and the sub-delims ! $ & ' ( ) * + , ; = — act as delimiters, so whether they must be encoded depends on where they appear.

JavaScript exposes two functions for this. encodeURI leaves the reserved characters untouched, because it assumes you are encoding an entire URL where :// and ?q= must stay literal. encodeURIComponent encodes those reserved characters too, because it targets a single component — a query value or a path segment — where a literal ? or & would be misread as a delimiter. For non-ASCII text such as Hangul, the text is first converted to its UTF-8 byte sequence and each byte is then percent-encoded; a single Korean character usually becomes three %XX groups.

Common use cases

  • Building a query string whose value contains spaces or non-ASCII text
  • Passing a redirect URL inside another URL as a parameter
  • Embedding JSON, Base64, or free-form search terms safely in a path
  • Handling Hangul, CJK, or emoji in shareable links
  • Debugging a broken link by inspecting or reverting percent-encoding

Worked example

Encoding a search URL whose query contains spaces and Korean text:

Input:
https://example.com/search?q=hello world 한국어

encodeURIComponent("hello world 한국어")
=> "hello%20world%20%ED%95%9C%EA%B5%AD%EC%96%B4"

Full encoded URL:
https://example.com/search?q=hello%20world%20%ED%95%9C%EA%B5%AD%EC%96%B4

The space becomes %20, and each Hangul syllable expands to three UTF-8 bytes (%ED%95%9C for 한, and so on). The reserved ? and = in the full URL are left intact, exactly as encodeURI would.

Frequently asked questions

What is percent-encoding?

Percent-encoding is the mechanism defined in RFC 3986 for representing characters inside a URI. Any byte that is not an unreserved character is written as a percent sign followed by the two hexadecimal digits of that byte, for example a space becomes %20.

What is the difference between encodeURI and encodeURIComponent?

encodeURI leaves reserved characters such as : / ? # [ ] @ intact, so it is meant for a whole URL. encodeURIComponent encodes those reserved characters too, so it is meant for a single query parameter value or path segment where they must not be treated as delimiters.

Why do spaces sometimes become %20 and sometimes +?

Both represent a space. %20 is the percent-encoded form used by RFC 3986 in the path and query. The plus sign is the older application/x-www-form-urlencoded form inherited from HTML forms. This tool uses the standard percent-encoded form (%20).

How are Korean or emoji characters encoded?

Non-ASCII characters are first converted to their UTF-8 byte sequence, then each byte is percent-encoded. Hangul is usually three bytes, so one Korean character turns into three %XX groups. Decoding reverses the process to recover the original text.

Is my input sent to a server?

No. Encoding and decoding run entirely in your browser using the native encodeURI and decodeURIComponent functions. Your input never leaves your device.

URL 인코더/디코더란?

URL(URI, RFC 3986에 정의됨)은 제한된 ASCII 문자만 담을 수 있습니다. 그 집합 밖의 모든 것 — 공백, 중괄호, 한글, 이모지, 최상위 비트가 1인 바이트 — 은 URL에 들어가기 전에 퍼센트 인코딩되어야 합니다. 이 도구는 그 인코딩과 역연산을 수행하여 경로나 쿼리 문자열에 임의 텍스트를 안전하게 넣고 나중에 원본을 되찾을 수 있게 합니다. 모든 처리는 브라우저에서 이루어지며 외부로 전송되지 않습니다.

작동 방식

퍼센트 인코딩은 바이트를 퍼센트 기호와 두 자리 16진수로 표기합니다: %XX. RFC 3986은 문자를 두 그룹으로 나눕니다. 비예약(unreserved) 문자 — A–Z, a–z, 0–9, 그리고 - . _ ~ — 은 특별한 의미가 없어 인코딩할 필요가 없습니다. 예약(reserved) 문자 — 일반 구분자 : / ? # [ ] @와 하위 구분자 ! $ & ' ( ) * + , ; = — 는 구분자 역할을 하므로, 인코딩해야 하는지는 등장 위치에 따라 다릅니다.

자바스크립트는 이를 위한 함수 두 개를 제공합니다. encodeURI는 예약 문자를 그대로 둡니다. 전체 URL을 인코딩한다고 가정하여 ://와 ?q=가 리터럴로 남아야 하기 때문입니다. 반면 encodeURIComponent는 예약 문자까지 인코딩합니다. 쿼리 값이나 경로 세그먼트 같은 단일 컴포넌트를 대상으로 하여, 리터럴 ?나 &가 구분자로 잘못 읽히는 것을 막습니다. 한글 같은 비-ASCII 텍스트는 먼저 UTF-8 바이트 시퀀스로 변환된 뒤 각 바이트가 퍼센트 인코딩되며, 한 글자는 보통 세 개의 %XX 그룹이 됩니다.

자주 쓰는 경우

  • 값에 공백이나 비-ASCII 텍스트가 있는 쿼리 문자열 만들기
  • 리다이렉트 URL을 다른 URL의 파라미터로 전달하기
  • JSON, Base64, 자유 형식 검색어를 경로에 안전하게 넣기
  • 공유 가능한 링크에서 한글, CJK, 이모지 처리하기
  • 퍼센트 인코딩을 검사하거나 되돌려 깨진 링크 디버깅하기

사용 예

쿼리에 공백과 한국어가 포함된 검색 URL을 인코딩하면:

Input:
https://example.com/search?q=hello world 한국어

encodeURIComponent("hello world 한국어")
=> "hello%20world%20%ED%95%9C%EA%B5%AD%EC%96%B4"

Full encoded URL:
https://example.com/search?q=hello%20world%20%ED%95%9C%EA%B5%AD%EC%96%B4

공백은 %20이 되고, 한글 음절 각각은 UTF-8 3바이트로 확장됩니다(한 → %ED%95%9C). 전체 URL 안의 예약 문자 ?와 =는 encodeURI가 하듯 그대로 남습니다.

자주 묻는 질문

퍼센트 인코딩이란 무엇인가요?

퍼센트 인코딩은 URI 안의 문자를 표현하기 위해 RFC 3986에 정의된 메커니즘입니다. 비예약 문자가 아닌 모든 바이트는 퍼센트 기호 뒤에 해당 바이트의 두 자리 16진수를 붙여 표기합니다. 예를 들어 공백은 %20이 됩니다.

encodeURI와 encodeURIComponent의 차이는?

encodeURI는 : / ? # [ ] @ 같은 예약 문자를 그대로 두어 전체 URL 용도로 쓰입니다. encodeURIComponent는 예약 문자까지 인코딩하여 단일 쿼리 파라미터 값이나 경로 세그먼트처럼 예약 문자가 구분자로 취급되면 안 되는 곳에 씁니다.

공백이 어떨 땐 %20, 어떨 땐 +가 되는 이유는?

둘 다 공백을 뜻합니다. %20은 RFC 3986에서 경로와 쿼리에 쓰는 퍼센트 인코딩 형태입니다. 더하기 기호는 HTML 폼에서 유래한 오래된 application/x-www-form-urlencoded 형태입니다. 이 도구는 표준 퍼센트 인코딩 형태(%20)를 사용합니다.

한국어나 이모지는 어떻게 인코딩되나요?

비-ASCII 문자는 먼저 UTF-8 바이트 시퀀스로 변환된 뒤 각 바이트가 퍼센트 인코딩됩니다. 한글은 보통 3바이트이므로 한 글자가 세 개의 %XX 그룹이 됩니다. 디코딩하면 과정이 역순으로 진행되어 원본 텍스트가 복원됩니다.

입력이 서버로 전송되나요?

아닙니다. 인코딩과 디코딩은 전적으로 브라우저에서 네이티브 encodeURI/decodeURIComponent 함수로 처리됩니다. 입력은 기기를 떠나지 않습니다.
