About the JWT Decoder

A JSON Web Token (JWT, RFC 7519) is a compact, URL-safe string used to assert claims between two parties, most commonly as a bearer credential after a user signs in to a web or mobile application. A JWT encodes a small JSON object that the server can read to identify a user, their roles, and an expiration, without a database lookup on every request. This decoder lets you inspect the contents of a token — its header, payload, and signature — entirely in your browser, which is exactly what you need when debugging authentication failures.

How it works

A JWT has three base64url-encoded parts joined by dots: header.payload.signature. The header declares the token type (typ) and the signing algorithm (alg, for example HS256 or RS256). The payload carries the claims — standard ones like sub (subject), exp (expiration), iat (issued-at), iss (issuer), and aud (audience), plus any custom claims. The signature is computed by the issuer over the base64url of the header and payload using the algorithm from the header and a secret (HMAC) or private key (RSA/ECDSA).

Base64url is the variant this tool must handle: it replaces + with - and / with _, and omits the = padding, so the token is safe inside URLs and headers. Decoding is just reversing that and parsing JSON — it is reading, not security. The critical distinction: decoding reveals the payload to anyone who has the token (a JWT is signed, not encrypted); only signature verification against the secret or public key proves the token was not tampered with. This tool decodes and reads only — it does not verify signatures, so never trust claims from an unverified token.

Common use cases

  • Inspecting a token returned by an OAuth2 or OpenID Connect server
  • Debugging an expired exp or wrong aud causing 401 responses
  • Auditing which claims and scopes an identity provider actually issued
  • Verifying the alg header before implementing server-side verification
  • Teaching how the three-part structure maps to header, payload, and signature

Worked example

Given this (unsigned, sample) token:

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkFkYSBMb3ZlbGFjZSIsImlhdCI6MTczNTY4OTYwMCwiZXhwIjoxNzM1Nzc2MDAwfQ.sOmE_s1gN0tBp2xV7l3oFakeSig

Decoding the first segment yields the header:

{ "alg": "HS256", "typ": "JWT" }

And the second segment yields the payload:

{
  "sub": "1234567890",
  "name": "Ada Lovelace",
  "iat": 1735689600,
  "exp": 1735776000
}

Anyone can reproduce this output from the token — that is why a JWT must never contain secrets, and why you must verify the signature before acting on the claims.

Frequently asked questions

Does decoding a JWT verify its signature?

No. Decoding only base64url-decodes the header and payload so you can read the claims. Proving authenticity requires signature verification against the secret or public key, which this tool does not perform. Never trust claims from an unverified token.

Is the JWT payload encrypted?

No. A standard JWT payload is base64url-encoded, not encrypted, so anyone who has the token can read it. Sensitive data must never be placed in a JWT payload unless you use a separate JSON Web Encryption (JWE) token.

What are the common payload claims?

Standard registered claims include sub (subject), iss (issuer), aud (audience), exp (expiration time), iat (issued-at time), and nbf (not-before time). Custom application-specific claims can also appear alongside them.

Why does my token fail to decode?

The most common causes are a truncated token, a missing third (signature) segment, copy-paste whitespace, or a JWE token that is encrypted rather than merely signed. The tool expects exactly three base64url parts separated by dots.

Is my token sent to a server?

No. All decoding runs locally in your browser, so live access tokens and credentials never leave your device. This makes the tool safe for inspecting real authentication tokens.

JWT 디코더란?

JSON Web Token(JWT, RFC 7519)은 두 주체 간에 클레임을 전달하기 위해 사용하는 간결하고 URL에 안전한 문자열로, 주로 사용자가 웹이나 모바일 애플리케이션에 로그인한 뒤 전달하는 베어러 자격증명으로 쓰입니다. JWT는 작은 JSON 객체를 인코딩하여 서버가 매 요청마다 데이터베이스를 조회하지 않고도 사용자와 역할, 만료 시간을 식별할 수 있게 해 줍니다. 이 디코더는 토큰의 내용 — 헤더, 페이로드, 서명 — 을 전적으로 브라우저 안에서 검사할 수 있게 해 주며, 인증 실패를 디버깅하거나 서버가 실제로 발급한 내용을 감사할 때 필요한 도구입니다.

작동 방식

JWT는 base64url로 인코딩된 세 부분을 점으로 이어 붙인 header.payload.signature 형태입니다. 헤더는 토큰 유형(typ)과 서명 알고리즘(alg, 예: HS256, RS256)을 선언합니다. 페이로드는 클레임을 담습니다 — sub(제목), exp(만료), iat(발급 시각), iss(발급자), aud(수신자) 같은 표준 클레임과 임의의 커스텀 클레임입니다. 서명은 발급자가 헤더와 페이로드의 base64url에 대해 헤더에 명시된 알고리즘과 비밀키(HMAC) 또는 개인키(RSA/ECDSA)로 계산합니다.

Base64url은 이 도구가 반드시 다뤄야 하는 변형입니다. + 대신 -를, / 대신 _를 쓰고 = 패딩을 생략하여 토큰이 URL과 헤더에 들어가도 안전합니다. 디코딩은 이를 역으로 되돌리고 JSON을 파싱하는 것일 뿐, 읽기이지 보안이 아닙니다. 핵심적인 구분: 디코딩은 토큰을 가진 누구나 페이로드를 볼 수 있게 합니다(JWT는 암호화가 아니라 서명된 값입니다). 서명 검증만이 비밀키 또는 공개키로 토큰이 변조되지 않았고 진짜 발급자에게서 왔음을 증명합니다. 이 도구는 디코딩/읽기만 하고 서명을 검증하지 않으므로, 검증되지 않은 토큰의 클레임은 절대 신뢰하지 마세요.

자주 쓰는 경우

  • OAuth2 또는 OpenID Connect 서버가 반환한 토큰 검사
  • 만료된 exp 또는 잘못된 aud로 인한 401 응답 디버깅
  • ID 공급자가 실제로 발급한 클레임과 스코프 감사
  • 서버 측 검증을 구현하기 전 alg 헤더 확인
  • 세 부분 구조가 헤더, 페이로드, 서명에 어떻게 대응되는지 학습

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkFkYSBMb3ZlbGFjZSIsImlhdCI6MTczNTY4OTYwMCwiZXhwIjoxNzM1Nzc2MDAwfQ.sOmE_s1gN0tBp2xV7l3oFakeSig

첫 번째 세그먼트를 디코딩하면 헤더가 나옵니다:

{ "alg": "HS256", "typ": "JWT" }

두 번째 세그먼트는 페이로드를 반환합니다:

{
  "sub": "1234567890",
  "name": "Ada Lovelace",
  "iat": 1735689600,
  "exp": 1735776000
}

누구나 토큰에서 이 출력을 재현할 수 있습니다 — 그래서 JWT에 비밀을 담으면 안 되며, 클레임에 의존해 행동하기 전에 반드시 서명을 검증해야 합니다.

자주 묻는 질문

JWT를 디코딩하면 서명이 검증되나요?

아닙니다. 디코딩은 헤더와 페이로드를 base64url 디코딩하여 클레임을 읽을 수 있게 할 뿐입니다. 진위를 증명하려면 비밀키 또는 공개키로 서명 검증을 해야 하며 이 도구는 그 단계를 수행하지 않습니다. 검증되지 않은 토큰의 클레임은 절대 신뢰하지 마세요.

JWT 페이로드는 암호화되어 있나요?

아닙니다. 표준 JWT 페이로드는 암호화가 아니라 base64url로 인코딩된 값이므로 토큰을 가진 누구나 읽을 수 있습니다. 민감한 데이터는 별도의 JSON Web Encryption(JWE) 토큰을 쓰지 않는 한 JWT 페이로드에 두면 안 됩니다.

페이로드의 일반적인 클레임은?

표준 등록 클레임으로 sub(제목), iss(발급자), aud(수신자), exp(만료 시각), iat(발급 시각), nbf(시작 시각)가 있으며, 애플리케이션 고유의 커스텀 클레임도 함께 들어갈 수 있습니다.

토큰이 디코딩에 실패하는 이유는?

가장 흔한 원인은 토큰이 잘린 경우, 세 번째(서명) 세그먼트가 누락된 경우, 복사-붙여넣기 과정의 공백, 또는 단순 서명이 아니라 암호화된 JWE 토큰인 경우입니다. 이 도구는 점으로 구분된 base64url 세 부분을 정확히 기대합니다.

제 토큰이 서버로 전송되나요?

아닙니다. 모든 디코딩은 브라우저에서 로컬로 실행되므로 실제 액세스 토큰과 자격증명이 기기를 떠나지 않습니다. 그래서 실제 인증 토큰을 검사하기에도 안전합니다.
