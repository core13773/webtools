About the Slug Generator

A URL slug is the human-readable tail of a web address — the part after the domain that identifies a page, such as how-to-bake-bread in example.com/blog/how-to-bake-bread. Good slugs are short, lowercase, descriptive, and use hyphens to separate words, which helps search engines and readers understand the page at a glance. The Slug Generator turns an arbitrary title into such a slug automatically, applying normalization and cleaning rules that would otherwise be a tedious manual edit.

How it works

The pipeline applies a fixed sequence of transforms. First the input is lowercased. Next, accented characters are normalized with Unicode NFKD decomposition: a composed character such as é is split into its base letter e plus a combining acute accent, and the combining marks are then stripped, so é collapses to e. After folding, punctuation and symbols are removed and every run of whitespace (spaces, tabs, newlines) is replaced with a single separator — a hyphen by default, or an underscore if you select it. Consecutive separators are collapsed and leading or trailing ones are trimmed. The result contains only URL-safe characters.

The reason for NFKD rather than NFC is decomposition: NFKD breaks composed forms into base plus diacritics, which is what lets the stripper recover the plain ASCII letter. Scripts that NFKD does not map to ASCII (Hangul, CJK, Cyrillic, Arabic) need an additional transliteration step that substitutes a romanized equivalent — for example romanizing the Korean greeting to annyeong — because stripping them outright would lose the word. Hyphens are preferred over underscores because search engines treat a hyphen as a word boundary.

Common use cases

  • Generating SEO-friendly permalinks for blog posts and articles
  • Creating product or category URLs from marketing titles
  • Building anchor links and fragment identifiers from headings
  • Producing kebab-case keys for documentation pages
  • Cleaning pasted titles into safe filename or path segments

Worked example

Take the mixed-language title:

Héllo, World! 안녕

Lowercasing and NFKD normalization fold é to e and strip the punctuation, then whitespace runs become hyphens. With a transliteration step applied to the Hangul, the final slug is:

hello-world-annyeong

If transliteration is disabled the Hangul is dropped instead, leaving hello-world — still URL-safe, but missing the second word.

Frequently asked questions

What makes a good URL slug?

A good slug is lowercase, short, descriptive, and uses hyphens to separate words. It contains only URL-safe ASCII characters, avoids punctuation and spaces, and reads naturally so both search engines and humans can understand the page topic from the URL alone.

How are accented characters handled?

Accented characters are normalized with Unicode NFKD, which decomposes a composed character into its base letter plus combining marks. The combining marks are then stripped, so e-with-acute becomes plain e. This folds most Latin accents to their ASCII equivalent.

Why hyphens instead of underscores?

Google treats a hyphen as a word separator but not an underscore, so hello-world is read as two words while hello_world is read as one. Hyphens are also reserved characters that never need encoding in a URL path, making them the safer choice for readability and SEO.

What happens to non-ASCII scripts like Korean?

NFKD normalization does not decompose Hangul into ASCII, so the default pipeline strips or transliterates those characters depending on the tool's mode. For full international slugs you may need a dedicated transliteration step that maps each syllable to a romanized form (for example annyeong) before generating the slug.

Is my text sent to a server?

No. Slugs are generated entirely in your browser through string normalization and replacement. Nothing is uploaded, so the tool is safe for unpublished titles, draft content, and confidential material.

슬러그 생성기란?

URL 슬러그는 웹 주소의 사람이 읽을 수 있는 끝부분입니다. 도메인 뒤에 붙어 한 페이지를 식별하는 부분으로, example.com/blog/how-to-bake-bread에서 how-to-bake-bread가 슬러그입니다. 좋은 슬러그는 짧고, 소문자이며, 설명적이고, 단어를 하이픈으로 구분합니다. 그래야 검색엔진과 독자 모두 URL만 봐도 페이지를 파악할 수 있습니다. 슬러그 생성기는 임의의 제목이나 헤딩을 이런 슬러그로 자동 변환하며, 직접 하면 귀찮을 정규화와 정리 작업을 한 번에 처리해 줍니다.

작동 방식

파이프라인은 고정된 변환 순서를 따릅니다. 먼저 입력을 소문자로 변환합니다. 다음으로 악센트가 있는 문자를 유니코드 NFKD 분해로 정규화합니다. 합쳐진 문자 é는 기본 글자 e와 결합 악센트로 분해되고, 결합 부호가 제거되면서 é는 e로 합쳐집니다. 폴딩이 끝나면 구두점과 기호를 제거하고, 공백 문자열(스페이스, 탭, 줄바꿈)을 하나의 구분자 — 기본값은 하이픈, 선택 시 밑줄 — 로 바꿉니다. 연속된 구분자는 하나로 합쳐지고 앞뒤 구분자는 다듬습니다. 결과에는 URL에 안전한 문자만 남습니다.

NFC가 아니라 NFKD를 쓰는 이유는 분해 때문입니다. NFKD는 합쳐진 형태를 기본 글자와 분음 부호로 나누어 주므로, 제거 단계에서 순수 ASCII 글자를 복원할 수 있습니다. NFKD가 ASCII로 매핑하지 않는 문자 체계(한글, 한자, 키릴, 아랍어 등)에는 추가 음역(transliteration) 단계가 필요합니다. 각 문자를 로마자 표기로 치환하는 단계로, 한국어 인사를 annyeong으로 바꾸는 식입니다. 이 단계 없이 통째로 지우면 단어가 사라지기 때문입니다. 하이픈을 밑줄보다 선호하는 이유는 검색엔진이 하이픈을 단어 경계로 인식하기 때문입니다.

자주 묻는 질문

좋은 URL 슬러그의 조건은?

좋은 슬러그는 소문자이고, 짧고, 설명적이며, 단어를 하이픈으로 구분합니다. URL에 안전한 ASCII 문자만 포함하고 구두점과 공백을 피하며, 자연스럽게 읽혀서 검색엔진과 사람 모두 URL만으로 페이지 주제를 이해할 수 있어야 합니다.

악센트 문자는 어떻게 처리되나요?

악센트 문자는 유니코드 NFKD로 정규화되어 합쳐진 문자를 기본 글자와 결합 부호로 분해합니다. 그다음 결합 부호를 제거하므로 e-with-acute는 순수 e가 됩니다. 이 과정이 대부분의 라틴 악센트를 해당 ASCII 글자로 폴딩합니다.

왜 밑줄 대신 하이픈인가요?

구글은 하이픈은 단어 구분자로 인식하지만 밑줄은 그렇지 않습니다. 그래서 hello-world는 두 단어로, hello_world는 한 단어로 읽힙니다. 하이픈은 URL 경로에서 인코딩이 필요 없는 예약 문자이기도 하므로 가독성과 SEO 모두에서 더 안전한 선택입니다.

한국어 같은 비 ASCII 문자는 어떻게 되나요?

NFKD 정규화는 한글을 ASCII로 분해하지 않으므로, 기본 파이프라인은 도구 모드에 따라 이 문자들을 제거하거나 음역합니다. 완전한 다국어 슬러그를 원하면 슬러그 생성 전에 각 음절을 로마자 표기(예: annyeong)로 매핑하는 전용 음역 단계가 필요할 수 있습니다.

제 텍스트가 서버로 전송되나요?

아닙니다. 슬러그는 전적으로 브라우저에서 문자열 정규화와 치환으로 생성됩니다. 업로드되는 것은 없으므로 미공개 제목, 초안 콘텐츠, 기밀 자료에도 안전합니다.
