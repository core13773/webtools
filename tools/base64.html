About the Base64 Encoder / Decoder

Base64 (defined in RFC 4648) is a binary-to-text encoding that represents arbitrary bytes using only 64 printable ASCII characters: the uppercase letters A–Z, lowercase a–z, digits 0–9, and the symbols + and /, with = used as padding. It exists because many protocols — email, HTTP headers, JSON strings — can only safely carry text, so any binary payload must first be turned into bytes that fall inside the ASCII safe range.

How it works

The encoder treats the input as a stream of bits and reads it in groups of 6. Because three bytes hold 24 bits (3 × 8), they split exactly into four 6-bit indices, and each index selects one character from the 64-symbol Base64 alphabet. Those four characters form one output unit. When the input length is not a multiple of three bytes, the final group is padded: one leftover byte produces two characters plus ==, and two leftover bytes produce three characters plus =. This is why a single = means one byte was left over and == means two. The + and / symbols (and = padding) are not URL-safe, so URL-safe Base64 variants swap them for - and _.

A side effect of carrying 6 bits per character is that the output grows to roughly 133% of the input size (4 characters per 3 bytes), so Base64 is an encoding, not compression — and definitely not encryption. It is fully reversible: anyone with the string can decode it back to the original bytes. Treat it as a transport shape, never as a way to hide a secret.

Common use cases

  • Embedding small images or fonts as data: URIs directly in HTML or CSS
  • Encoding credentials for HTTP Basic Auth (user:pass → Authorization header)
  • Carrying the three dot-separated segments of a JWT (header.payload.signature)
  • Attaching binary files inside MIME email (Content-Transfer-Encoding: base64)
  • Storing binary blobs in JSON or XML, which only accept text

Worked example

Encoding the 5-character string Hello:

Input text:  Hello
UTF-8 bytes: 48 65 6C 6C 6F  (5 bytes)
Base64:      SGVsbG8=

The first three bytes (H, e, l) map to SGVs, the next two (l, o) form an incomplete triple, so they become bG8= with one = pad. Decoding SGVsbG8= reverses every step and returns Hello exactly.

Frequently asked questions

Is Base64 encryption?

No. Base64 is an encoding, not encryption. It is fully reversible and uses a public, well-known alphabet, so anyone can decode it. It only transforms data into a text-safe shape; it provides zero confidentiality and must never be used to protect secrets.

Why does the output get longer than the input?

Every 3 input bytes (24 bits) become 4 Base64 characters, so the encoded text is about 33% larger than the raw bytes. Any leftover bytes at the end are padded with = characters to reach a multiple of 4 characters.

What do the = signs at the end mean?

They are padding. When the input length is not a multiple of 3 bytes, the final 6-bit group is incomplete, so = is appended to make the total character count a multiple of 4. One = means one leftover byte; two = means two leftover bytes.

Does this tool support UTF-8 text like Korean?

Yes. The text is first encoded to UTF-8 bytes, and those bytes are then Base64-encoded. Multibyte characters such as Hangul, emoji, or CJK text are handled correctly, and decoding reverses the process back to the original string.

Is my data sent to a server?

No. Encoding and decoding run entirely in your browser using the native btoa and atob functions. Your input never leaves your device, so it is safe for tokens and sensitive values.

Base64 인코더/디코더란?

Base64(RFC 4648에 정의됨)는 임의의 바이트를 64개의 출력 가능한 ASCII 문자로 표현하는 바이너리-투-텍스트 인코딩입니다. 사용하는 문자는 대문자 A–Z, 소문자 a–z, 숫자 0–9, 그리고 기호 +와 /이며, 패딩에는 =를 씁니다. 이 인코딩이 존재하는 이유는 이메일, HTTP 헤더, JSON 문자열 같은 많은 프로토콜이 텍스트만 안전하게 전달할 수 있기 때문이며, 따라서 모든 바이너리 페이로드는 ASCII 안전 범위 안의 바이트로 먼저 변환되어야 합니다.

작동 방식

인코더는 입력을 비트 스트림으로 간주하고 6비트 단위로 읽습니다. 세 바이트는 24비트(3 × 8)를 담으므로 정확히 네 개의 6비트 인덱스로 나뉘며, 각 인덱스는 64개의 Base64 알파벳에서 문자 하나를 선택합니다. 이 네 문자가 하나의 출력 단위가 됩니다. 입력 길이가 3바이트의 배수가 아니면 마지막 그룹은 패딩됩니다. 남은 바이트가 하나이면 두 문자와 ==가, 두 개이면 세 문자와 =가 붙습니다. 그래서 = 하나는 남은 바이트가 하나, ==는 남은 바이트가 둘임을 뜻합니다. +와 / 기호(그리고 = 패딩)는 URL에 안전하지 않아서, URL 안전 Base64 변형은 이를 -와 _로 바꿉니다.

문자당 6비트를 담는 부수 효과로 출력은 입력 크기의 약 133%(3바이트당 4문자)로 커집니다. 따라서 Base64는 인코딩일 뿐 압축이 아니며, 더더욱 암호화도 아닙니다. 완전히 가역적이어서 문자열을 가진 누구나 원래 바이트로 디코딩할 수 있습니다. 전송 형태로만 다루고, 비밀을 숨기는 용도로는 절대 쓰지 마세요.

자주 쓰는 경우

  • 작은 이미지나 폰트를 HTML/CSS에 data: URI로 직접 임베드하기
  • HTTP Basic Auth 자격증명 인코딩(user:pass → Authorization 헤더)
  • JWT의 점으로 구분된 세 세그먼트(header.payload.signature) 전달하기
  • MIME 이메일 안에 바이너리 파일 첨부(Content-Transfer-Encoding: base64)
  • 텍스트만 받는 JSON이나 XML에 바이너리 블롭 저장하기

사용 예

5글자 문자열 Hello를 인코딩하면:

Input text:  Hello
UTF-8 bytes: 48 65 6C 6C 6F  (5 bytes)
Base64:      SGVsbG8=

처음 세 바이트(H, e, l)는 SGVs로, 다음 두 바이트(l, o)는 불완전한 세 묶음이 되어 = 패드 하나와 함께 bG8=가 됩니다. SGVsbG8=를 디코딩하면 모든 단계가 역순으로 진행되어 정확히 Hello가 돌아옵니다.

자주 묻는 질문

Base64가 암호화인가요?

아닙니다. Base64는 인코딩이지 암호화가 아닙니다. 완전히 가역적이며 공개된 알파벳을 쓰므로 누구나 디코딩할 수 있습니다. 데이터를 텍스트 안전 형태로 바꿀 뿐 기밀성은 전혀 제공하지 않으므로 비밀을 보호하는 용도로는 절대 쓰면 안 됩니다.

왜 출력이 입력보다 길어지나요?

입력 3바이트(24비트)가 4개의 Base64 문자가 되므로, 인코딩된 텍스트는 원시 바이트보다 약 33% 더 깁니다. 끝에 남은 바이트는 총 문자 수가 4의 배수가 되도록 = 문자로 패딩됩니다.

끝의 = 기호는 무슨 뜻인가요?

패딩입니다. 입력 길이가 3바이트의 배수가 아니면 마지막 6비트 그룹이 불완전해져서, 전체 문자 수를 4의 배수로 맞추기 위해 =를 붙입니다. = 하나는 남은 바이트가 하나, ==는 남은 바이트가 둘임을 뜻합니다.

한국어 같은 UTF-8 텍스트도 지원되나요?

네. 텍스트는 먼저 UTF-8 바이트로 인코딩된 뒤 그 바이트가 Base64로 인코딩됩니다. 한글, 이모지, CJK 문자 같은 멀티바이트 문자도 올바르게 처리되며, 디코딩하면 원래 문자열로 되돌아갑니다.

데이터가 서버로 전송되나요?

아닙니다. 인코딩과 디코딩은 전적으로 브라우저 안에서 네이티브 btoa/atob 함수로 처리됩니다. 입력은 기기를 떠나지 않으므로 토큰이나 민감한 값에도 안전합니다.
